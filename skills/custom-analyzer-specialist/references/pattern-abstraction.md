# パターン抽象化の方法論

具体的なレガシーコードの断片を、アナライザーで検出可能なルールへ昇華するための詳細ガイド。

## 抽象化とは何をすることか

「このコードは悪い」から「このコードベースでは不変条件 X が破られがちで、それは構文/意味パターン Y として検出できる」
へ言い換えることである。良い抽象化は次の3つを同時に満たす:

1. **不変条件が一文で言える** — 「例外は観測可能でなければならない」「SQL への入力はパラメータ化されなければならない」
2. **検出条件が形式的に定義できる** — SyntaxKind とシンボル条件の組み合わせで書き下せる
3. **反例（検出してはいけないコード）が列挙できる** — 反例が思いつかないルールは、まだ考察が足りない

## 手順

### 1. 具体例を並べて共通部分と差分を見る

収集した3件以上の具体例を並べ、「何が共通か」「何が違うか」を観察する。

```csharp
// 例: 「SQL文字列連結」の具体例3件
cmd.CommandText = "SELECT * FROM Users WHERE Id = " + id;
var sql = string.Format("DELETE FROM {0} WHERE Key = '{1}'", table, key);
cmd.CommandText = $"UPDATE Orders SET Status = {status}";
```

共通: 実行される SQL 文字列に非リテラルが混入している。
差分: 連結演算子 / string.Format / 補間文字列、代入先が変数 or プロパティ。

→ 字面（`+` 演算子）で捉えると string.Format と補間を漏らす。
**不変条件は「`CommandText` に渡る文字列が定数でないこと」**であり、これは意味レベルの条件。

### 2. 検出条件を「トリガー + フィルタ」で書き下す

- **トリガー**: どの構文ノード/シンボルに反応するか（SyntaxKind / SymbolKind）
- **フィルタ**: そのうちどれを違反とみなすか（意味条件、早期リターンの連鎖で書く）

```text
ルール: LEG002 SQL文字列連結
トリガー: SimpleAssignmentExpression, ObjectCreationExpression（SqlCommand の引数）
フィルタ:
  - 代入先シンボルが System.Data.*.CommandText であること（SemanticModel で解決）
  - 右辺の定数値解決（SemanticModel.GetConstantValue）が失敗すること
反例（検出しない）:
  - const 文字列や readonly リテラルの代入
  - パラメータプレースホルダのみの動的組み立て（テーブル名の switch など）→ 初版では許容して検出、
    誤検知報告が出たら suppression 手段を案内
```

### 3. 反例リストを作ってから実装する

反例はそのままユニットテストの「警告が出てはいけないケース」になる。
反例を出す質問:

- 同じ構文で**正当な**コードは書けるか？
- 生成コード（Designer.cs）にこのパターンは現れるか？
- テストコードでは意図的にこのパターンを使っていないか？
- null 許容・ジェネリクス・部分クラス・ネストで壊れないか？

## 修正可能性 A/B/C の判定基準

### A（機械修正可）と判定してよい条件 — すべて満たすこと

- 変換前後でプログラムの観測可能な挙動が**あらゆる文脈で**等価
- 変換に必要な情報がすべて構文/意味モデルから機械的に得られる
- 変換結果が対象プロジェクトの LanguageVersion でコンパイル可能

例: `throw ex;` → `throw;`（catch 変数を再送出している場合）、
非ジェネリック `ArrayList` のうち単一型しか入れていないことが証明できるローカル変数の `List<T>` 化（証明できる場合のみ）。

### B（検出のみ）に落とすべきサイン

- 「正しい修正」が業務文脈に依存する（空 catch: ログ？再送出？本当に無視が正しい？）
- 挙動が変わる（`DateTime.Now` → `UtcNow` は保存済みデータとの整合が壊れうる）
- 修正に新しい依存や設計判断が要る（`IClock` 注入、パラメータ化クエリへの書き換え）

B のルールでも価値は大きい。「どこに何件あるか」が見えるだけで改善計画が立つ。

### C（ルール化不適）のサイン

- 具体例が2件以下
- 検出条件に「〜のような」「〜と思われる」が残る（形式化できていない）
- メトリクス系で閾値が恣意的（メソッド行数など）→ 導入するなら severity は info 止まりにし、
  チームで閾値に合意してから

## Diagnostic メッセージの書き方

メッセージは「何が悪いか」ではなく「**何をすべきか + なぜか**」を書く。開発者が読むのはビルドログの1行だけ。

```text
悪い: 空のcatchブロックがあります
良い: 例外を握りつぶさず、ログ出力・再送出・または無視する理由のコメントを追加してください（LEG001）
```

MessageFormat には具体的なシンボル名をプレースホルダで入れる（`'{0}' が Dispose されていません`）。
