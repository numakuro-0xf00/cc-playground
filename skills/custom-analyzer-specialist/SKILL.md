# Custom Analyzer Specialist

レガシーコードベースを「1ファイルずつ手で直す」のではなく、
**問題を検出ルールとして抽象化し、アナライザー＋コードフィックスでコードベース全体に適用する**ためのスキル。

## このスキルの位置づけ

- **本スキル**: 何を検出すべきかの発見・抽象化・ルール設計・改善戦略・ロールアウト（戦略レイヤー）
- **`skills/roslyn-analyzer`**: アナライザー/コードフィックスの実装・テスト・配布のメカニクス（実装レイヤー）

実装フェーズに入ったら必ず `skills/roslyn-analyzer/SKILL.md` を読み、そちらの手順に従うこと。
コード調査には `roslyn-query` スキル（定義ジャンプ・参照検索・コール階層）が利用可能なら積極的に使う。

## なぜアナライザーで改善するのか

レガシー改善が失敗する典型は「その場で見つけた箇所だけ直す」こと。同じ問題は他に何十箇所も存在し、
新しいコードでも再生産され続ける。アナライザー化すると:

1. **網羅性** — コンパイラが全ソースを走査するので、見落としがない
2. **再発防止** — CI で新規違反をブロックできる（ラチェット）
3. **修正の一貫性** — CodeFix による機械的修正は人手より安全で一様
4. **知識の資産化** — 「このコードベースで何が危険か」がルールとして形式知になる

## ワークフロー全体像

```
PHASE 1  調査      レガシーコードを読み、問題の「具体例」を収集する
PHASE 2  抽象化    具体例を検出可能なルールへ昇華し、修正可能性を分類する
PHASE 3  カタログ  ルールカタログを作り、優先順位を付け、ユーザーと合意する
PHASE 4  実装      アナライザー＋コードフィックスを実装しテストする（→ roslyn-analyzer スキル）
PHASE 5  展開      ベースライン計測 → 一括修正 → severity ラチェットで定着させる
```

各フェーズの終わりに成果物（発見リスト / ルールカタログ / 実装 / ロールアウト計画）を提示し、
方向性をユーザーと確認してから次へ進む。**PHASE 3 のカタログ合意前に実装を始めないこと。**
非対話（subagent 等）で実行されている場合は、合意の代わりにカタログを成果物として記録し、
優先度1のルールから順に進めてよい。判断に迷った選択は最終報告に明記する。

## PHASE 1: レガシーコード調査

目的は「悪い箇所を直すこと」ではなく「**繰り返されている問題パターンの具体例を集めること**」。

### 調査の観点

- 例外処理: 握りつぶし（空 catch）、`throw ex` によるスタックトレース破壊
- リソース管理: `IDisposable` の Dispose 漏れ、コネクション/ストリームのリーク
- セキュリティ: SQL 文字列連結、パス結合の手組み
- 型とコレクション: `ArrayList`/`Hashtable` 等の非ジェネリック、object 経由のキャスト
- 文化圏・時刻: `DateTime.Now` 直呼び、カルチャ未指定の文字列比較・変換
- 構造: God メソッド、static 可変状態、コピペ重複

頻出パターンの詳細（検出戦略・修正戦略・誤検知の注意つき）は
→ `references/legacy-pattern-catalog.md`

### 調査のやり方

1. まず Grep で「疑わしい字面」を横断検索し、当たりをつける（`catch { }`, `ArrayList`, `DateTime.Now`, `+ "SELECT` など）
2. ヒットした箇所を実際に読み、**前後の文脈ごと** 3件以上の具体例をパターンごとに記録する
3. `roslyn-query` が使えるなら参照検索・コール階層で影響範囲を確認する
4. 発生件数の概算を取る（後の優先順位付けに使う）

件数は**違反の出現箇所単位**で数える（1メソッド内に3箇所あれば3件。ファイル数ではない）。
具体例が1〜2件しかないものは**実装しない**（カタログには分類 C として載せてよい — 「載せない」ではなく
「アナライザー化しない判断を記録する」が正しい扱い）。個別修正のほうが安い。

## PHASE 2: パターンの抽象化とルール設計

このスキルの核心。**具体例の字面ではなく、破られている不変条件（invariant）を特定する。**

### 抽象化の3ステップ

1. **解釈**: この具体例は何を壊しているのか？（リソース安全性 / 例外の可観測性 / インジェクション耐性 / カルチャ正当性 …）
2. **昇華**: その不変条件の違反を、どの抽象度で検出できるか？（抽象化の梯子 — 下記）
3. **分類**: 検出したものを機械が直せるか、人が判断すべきか？

### 抽象化の梯子（低い段で足りるならそれを選ぶ）

| 段 | 手段 | 例 |
|---|---|---|
| 字面 | 正規表現（調査用のみ。アナライザーには使わない） | `"SELECT " +` |
| 構文 | `RegisterSyntaxNodeAction` + SyntaxKind | 空の CatchClause |
| 意味 | SemanticModel で型・シンボルを解決 | `SqlCommand.CommandText` への連結代入 |
| フロー | Operation/DataFlow 解析 | Dispose されずスコープを抜ける local |

段が上がるほど誤検知は減るが実装コストが増える。
**誤検知の許容量はゼロに近い**と考えること。レガシー導入で最初に信頼を失う原因は誤検知ノイズである。
再現率（漏れ）より適合率（誤検知のなさ）を優先する。

### 修正可能性の3分類

| 分類 | 意味 | 出力 |
|---|---|---|
| A: 機械修正可 | 文脈によらず等価変換できる | Analyzer + CodeFix（FixAll 対応） |
| B: 検出のみ | 修正には人間の文脈判断が要る | Analyzer のみ（severity で通知） |
| C: ルール化不適 | 検出自体に判断が要る／例が少なすぎる | レビュー観点として文書化、アナライザーにしない |

C を無理にアナライザー化しないこと。判断をルールに押し込むと誤検知製造機になる。

抽象化の詳細な方法論・判断基準は → `references/pattern-abstraction.md`

## PHASE 3: ルールカタログと優先順位付け

ルールごとに1行で管理するカタログを作り、ユーザーに提示して合意を取る。

```markdown
| ID | ルール名 | 分類 | 不変条件 | 概算件数 | 誤検知リスク | 優先度 |
|--------|--------------------------|---|------------------------|------|---|---|
| LEG001 | 空catchによる例外握りつぶし | A | 例外は観測可能であること | ~120 | 低 | 1 |
| LEG002 | SQL文字列連結             | B | 入力はパラメータ化されること | ~40  | 中 | 2 |
```

- ID プレフィックスはプロジェクト固有に決める（例: `LEG`）。番号は欠番を恐れず連番
- **優先度 = 発生頻度 × 障害リスク × 修正容易性 ÷ 誤検知リスク** を目安に判断する
- 最初の1本は「頻度が高く、機械修正でき、誤検知しにくい」ルールを選ぶ。
  初回で信頼を勝ち取ると以降の展開が楽になる

## PHASE 4: 実装

**ここからは `skills/roslyn-analyzer/SKILL.md` の STEP 1〜5 に従う。**
このリポジトリでは `Sample_Analyzer/` に「Analyzer with Code Fix」テンプレートの実物
（Analyzer / CodeFixes / Package / Test / Vsix、Roslyn 3.3.1 = VS2019 互換）があるので、
プロジェクト構成の参考および実装の土台として使える。既存プロジェクトを土台にする場合、
roslyn-analyzer スキルの STEP 1（VS でのテンプレート作成）はスキップする。本スキルからの追加要求は:

- 1ルール = 1 DiagnosticDescriptor。カタログの ID・不変条件を DiagnosticDescriptor の
  Title / Description にそのまま反映する
- 分類 A のルールは `FixAllProvider`（BatchFixer）を必ず有効にする — 一括修正が目的だから
- テストには **PHASE 1 で収集した実物の具体例**（匿名化して）をそのまま使う。
  合成例だけのテストは現場の形に負ける
- `ConfigureGeneratedCodeAnalysis(GeneratedCodeAnalysisFlags.None)` を必ず設定。
  レガシーには `*.Designer.cs`（WinForms/WebForms）が大量にあり、生成コードへの警告はノイズでしかない
- 既存プロジェクトへ2本目以降のルールを追加する場合、既存ルールの Resources.resx を書き換えて
  壊さないこと。追加ルールの Title / MessageFormat は plain string で定義してよい
  （ローカライズが必要になった時点で resx にルールIDプレフィックスつきキーとして追加する）

### .NET Framework 固有の制約（重要）

対象コードが .NET Framework（非 SDK 形式 csproj / packages.config / 古い C# バージョン）の場合、
アナライザーの参照方法・CodeFix が出力してよい構文・一括適用の手段に制約がある。
実装前に必ず → `references/netfx-constraints.md` を読むこと。
特に **CodeFix が対象プロジェクトの LanguageVersion より新しい構文を出力してはならない**点は事故が多い。

## PHASE 5: 段階的ロールアウト

一括で warning を投入するとビルドログが数百件の警告で埋まり、全員がアナライザーを憎むようになる。
必ず段階を踏む:

```
Phase 0  ベースライン計測   件数を記録（改善の証跡になる）
Phase 1  info/suggestion    ビルドに影響させず誤検知フィードバックを collect
Phase 2  一括修正           1ルール = 1PR で FixAll 適用。テストが通ることを確認
Phase 3  warning + CI ゲート 新規違反のみブロック（ラチェット）
Phase 4  error              定着
```

severity 制御（.editorconfig / ruleset）、旧形式プロジェクトでの設定方法、
CI 連携、ラチェットの具体的な仕組みは → `references/rollout-strategy.md`

### 挙動保存の原則

一括修正 PR は**リファクタリングであってバグ修正ではない**。挙動を変える修正
（例: 空 catch にログを足す、`DateTime.Now` を `UtcNow` に変える）は分類 B として人間の判断に委ね、
CodeFix で自動適用するのは等価変換だけにする。テストが薄いレガシーでは特に厳守。

## 完了チェックリスト

```
□ 問題パターンごとに実例3件以上を収集した
□ 各ルールについて「破られている不変条件」を一文で言語化した
□ A/B/C 分類を行い、C を無理にアナライザー化していない
□ ルールカタログをユーザーに提示し、優先順位に合意を得た
□ 実装は roslyn-analyzer スキルの手順・チェックリストに従った
□ テストに実コードベース由来の具体例を含めた
□ .NET Framework 制約（LanguageVersion / 参照方法 / 一括適用手段）を確認した
□ ベースライン件数を計測・記録した
□ 一括修正は 1ルール=1PR で、既存テストが通ることを確認した
□ ラチェット（新規違反ブロック）を CI に設定した
```
